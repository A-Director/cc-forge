## Standards-grounding guarantee

Every item in this backlog carries a `**Standard:**` line pointing at a
real, externally-defined rule (OWASP ASVS, WCAG, GDPR Article, vendor
security doc, Google SRE Book chapter, etc.). This anchoring is what
makes the backlog auditable rather than opinion-shaped.

`/hermes-backlog-init` runs a verification step (Phase 6) that refuses
to complete if any customised item lost its **Standard:** line during
project-specific rewriting. If you see a backlog item in this file
without a **Standard:** line, the init was bypassed — re-run
`/hermes-backlog-init`.

Gate-review personas update items in this backlog as part of their
review, following the 3-step protocol in
`personas/_shared/backlog-update-protocol.md`. Every Taskmaster task
seeded from a persona finding carries its parent backlog ID and the
parent's Standard reference, so work-in-flight stays traceable.

**Orphan tasks** (tasks seeded with no parent backlog item) and
**missing coverage** events (findings with no matching template item)
are logged to `.cc-forge/usage.log` and indicate cc-forge framework
drift — they should be rare. The Session C dashboard surfaces both
counters.

## Launch readiness gate

A project is ready for public launch (Phase 4) when:
- Phase 4 domain bars met across 01–08 (see table above)
- Compliance domain (07) at 90%+
- No CRITICAL or HIGH items in RISKS.md without mitigation
- No BLOCK outcomes on any gate review
- `/hermes-phase-gate` from Pilot → Launch has passed

Domains 09 Growth and 10 Operations are post-launch focus — they
ramp during Phase 5 Growth.

## Status key

| Status | Meaning |
|---|---|
| `not-started` | Not yet worked on |
| `in-progress` | Being worked on this sprint |
| `done` | Complete — evidence recorded |
| `not-applicable` | Does not apply to this project — decision in DECISIONS.md |
| `operator-action` | Requires manual operator action outside the code (e.g. configure DNS, sign DPA, file SOC2 paperwork). Tracked separately from `in-progress` because it doesn't progress through code work. |

---

## Override rule

Any item marked `not-applicable` MUST have:
1. An entry in `DECISIONS.md` explaining why
2. An entry in `RISKS.md` if the item relates to security, reliability, or compliance

Hermes enforces this — a `not-applicable` without a decision record is flagged
by Argus as non-compliant.

Items marked `operator-action` should reference the runbook or
checklist entry that describes the manual step.
